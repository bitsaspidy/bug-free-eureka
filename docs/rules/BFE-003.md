## 1. Concern

An Express app that reads request bodies without a bounded size lets one client make the process buffer, parse and hold as much data as it can send. The usual outcomes are memory exhaustion and event-loop stalls (large JSON or urlencoded parsing), disk exhaustion (uploads to disk), and many-field or many-file requests that cost CPU long before any handler runs. Express's own parsers are safe by default (`limit` is `100kb` for json, urlencoded, raw and text), so the production problems come from changes to the defaults: `limit` raised globally "to make one upload work", set to `Infinity`, or `multer` mounted without `limits` (its `fileSize`, `files`, `fields` and `parts` default to unlimited). The risk is easy to misjudge in both directions. Teams assume a proxy (for example Nginx `client_max_body_size`) caps bodies when it does not, and scanners flag apps whose limit is set at a proxy, in a per-route parser, or by a streaming handler that counts bytes itself. This rule reports what the declared evidence shows and says `not_assessed` when it cannot see the layer that decides. A passing result does not mean the app is secure or resistant to denial of service. It means the body-reading declarations found were bounded within the default thresholds in the evidence supplied.

## 2. Inputs & evidence

The rule is a pure function of one typed input plus optional thresholds. Collectors (scanner, config loader) build the input. The rule performs no I/O and never reads the clock, the environment or the network. Size strings such as `"1mb"` are converted to bytes by the collector (same units as the `bytes` package: 1kb = 1024) so the rule compares integers only.

### 2.1 Proposed input type

```ts
export type Tri = "yes" | "no" | "unknown";

/** How a size value was observed. Only "literal" and "default" can ever support a pass. */
export type LimitValue =
  | { state: "default" }                     // option omitted: library default applies
  | { state: "literal"; bytes: number }      // integer >= 1, <= Number.MAX_SAFE_INTEGER
  | { state: "unbounded" }                   // literal Infinity, or a literal value above the safe integer range
  | { state: "non-literal" };                // variable, process.env, function, spread, call result

export type ParserKind = "json" | "urlencoded" | "raw" | "text" | "multer" | "custom-reader";
// "custom-reader": req.on("data"), busboy, formidable, raw-body, req.pipe(...) seen in source

export interface BodyDeclaration {
  kind: ParserKind;
  source: "express" | "body-parser" | "multer" | "other";    // express.json vs body-parser package
  scope: "global" | "route" | "conditional" | "unresolved";  // conditional = inside if/env check
  location: string;                                          // POSIX-relative "file:line"
  limit: LimitValue;                      // json/urlencoded/raw/text: `limit`. multer: limits.fileSize
  parameterLimit?: LimitValue;            // urlencoded only
  multer?: {                              // multer only
    storage: "memory" | "disk" | "unknown";
    limitsObject: "literal" | "absent" | "non-literal";
    files: LimitValue;                    // limits.files   (absent key = "default" = unlimited)
    fields: LimitValue;                   // limits.fields
    fieldSize: LimitValue;                // limits.fieldSize (default 1 MiB)
    parts: LimitValue;
  };
  byteCounted?: boolean;                  // custom-reader only: a literal running byte counter with abort was seen
}

export interface RequestSizeInput {
  app: {
    expressAppFound: boolean;
    expressMajor: 4 | 5 | "unknown";           // from the declared dependency range; evidence note only
    legacyBodyParser: boolean;                 // express.bodyParser() / connect.bodyParser (Express <4.16 era)
  };
  coverage: {
    complete: boolean;                         // false if any limit hit / file skipped / unparsed
    limitsHit: string[];                       // counts only are echoed
    unresolvedMiddleware: boolean;             // app built dynamically or aliases unresolved
  };
  declarations: BodyDeclaration[];             // max 200
  proxy: {
    present: Tri;                              // reverse proxy / CDN / gateway in front, as DECLARED
    bodyLimitConfig: "supplied" | "not_supplied";
    appReachableDirectly: Tri;                 // declared: can clients bypass the proxy
    // Parsed from supplied proxy config only. Absent when not supplied.
    nginx?: {
      clientMaxBodySize: Array<{
        scope: "http" | "server" | "location";
        value: { state: "literal"; bytes: number } | { state: "unlimited" } | { state: "non-literal" };
        // "unlimited" is the literal 0. A missing directive is NOT listed here; see D9.
        locationCount: number;                 // how many location blocks this entry covers; routes are never echoed
      }>;
      configComplete: boolean;                 // included files and variables all resolved
    };
    declaredLimit?: LimitValue;                // user-declared: "the proxy caps request bodies at N"
  };
}

export interface RequestSizeOptions {
  warnBytes: number;        // default 1_048_576   (1 MiB)   global json/urlencoded/text/raw above this: warning
  routeWarnBytes: number;   // default 10_485_760  (10 MiB)  route-scoped parsers above this: warning
  failBytes: number;        // default 104_857_600 (100 MiB) any parser above this: fail
  memoryUploadWarnBytes: number; // default 10_485_760 (10 MiB) multer memoryStorage fileSize above this: warning
  diskUploadWarnBytes: number;   // default 104_857_600 (100 MiB) multer diskStorage fileSize above this: warning
  parameterWarn: number;    // default 10_000  urlencoded parameterLimit above this: warning
  fieldsWarn: number;       // default 1_000   multer fields/parts above this: warning
  filesWarn: number;        // default 20      multer files above this: warning
}
```

### 2.2 Evidence ranking and base confidence

| Source | Meaning | Ceiling |
|---|---|---|
| Declared deployment config (user states the proxy cap and that clients cannot bypass it) | What reaches the app | high |
| Parsed proxy config file (`client_max_body_size` only) | Proxy cap for the covered scope | medium (includes, variables, `if` and location matching make parsing partial) |
| Source AST, literal `limit` options on `express.json` etc. | The app's own cap | medium (order, conditionals and other modules are not fully visible) |
| Source AST, option omitted | Library default applies (Express 4 and 5: `100kb`, see 2.4) | medium |
| `package.json` dependency hint (`multer`, `body-parser` listed) | Parser exists somewhere | low, and never enough alone |

Spread-out setup (router factories, parsers mounted in another module) lowers confidence one level and the evidence text says so (static-analysis-safety).

### 2.3 Allowlist, caps and redaction (BFE-001 lessons)

* Evidence strings contain only: parser kind (fixed enum), `source` and `scope` (fixed enums), normalized integers (bytes, counts), fixed verdict phrases, and a location only when it matches `^[\w./-]{1,200}:\d{1,9}$`; anything else is replaced by the constant `unknown-location`. Route paths, option expressions, variable names, `limitsHit` text, file names and any raw source text are never echoed (counts only).
* Input caps enforced by the Zod schema (reject, never truncate silently): `declarations` at most 200; each `location` at most 500 chars; `limitsHit` at most 200 entries of at most 500 chars; `nginx.clientMaxBodySize` at most 200 entries; `bytes` and counts must be integers from 1 to `Number.MAX_SAFE_INTEGER`; unknown keys rejected. At most 20 declarations are itemized in evidence, then "and N more declarations".
* Unknown enum values, `NaN`, negative numbers, or `0` parse as a validation error (the engine surfaces it as a typed error), not as a limit. Collectors map `limit: 0` on a body-parser option to `non-literal` (its behavior is easy to misread), and the literal `Infinity` to `unbounded`.
* Thresholds come from `RequestSizeOptions` (validated, finite, ordered `warnBytes <= failBytes`); defaults above.

### 2.4 Library defaults (pinned, deterministic)

Verified on 2026-11-16 against the body-parser and multer documentation (see References). The rule applies this table when an option is omitted. If the package or major is not listed, the state is `non-literal`-like: `not_assessed`, never pass.

| Parser | Option omitted means | Notes |
|---|---|---|
| `express.json`, `express.urlencoded`, `express.raw`, `express.text` (Express 4.16+ and 5) and `body-parser` json/urlencoded/raw/text | `limit` is `100kb` | Same value in Express 4 and 5 (body-parser 1.x and 2.x). Exceeding it gives 413 `entity.too.large` |
| `express.urlencoded` / `bodyParser.urlencoded` | `parameterLimit` is `1000` | Exceeding it gives 413 `parameters.too.many` |
| `inflate` | `true`: compressed bodies are decompressed first | The limit applies to the inflated size per body-parser docs; the rule does not model compression ratios |
| `multer` `limits.fileSize`, `files`, `fields`, `parts` | Unlimited (`Infinity`) | Only `fieldSize` (1 MiB) and `headerPairs` (2000) are finite by default |
| `multer` with no `limits` option at all | Everything above unlimited | `limitsObject: "absent"` |

Express 4 versus 5, only where it matters here: (a) the byte limits are identical, so `expressMajor` never changes a decision; (b) `urlencoded` `extended` defaults to `true` in Express 4 and `false` in Express 5, which changes nested-object parsing cost (qs) but not the byte cap, so it appears only as an evidence note; (c) `req.body` is `{}` in Express 4 and `undefined` in Express 5 when no parser matched, which is not evidence either way. Express before 4.16 (`express.bodyParser()`, `legacyBodyParser: true`) is `not_assessed`: it is unsupported and its limits are not modeled here.

Behavior the rule relies on, to be confirmed by a unit test against the real packages during implementation (not asserted from memory): a body-parser instance skips a request already parsed by an earlier parser, so for a given content type the first matching mounted parser decides the limit.

## 3. Decision table

### 3.1 Per-declaration state

Evaluate in order for each declaration `d`. First matching row wins. "Bounded" means `limit` is `default` or `literal` at or below the applicable threshold.

| # | Condition | Per-declaration state | Confidence |
|---|---|---|---|
| P1 | `scope` is `conditional` or `unresolved` | not_assessed ("declared inside a condition or an unresolved module; production behavior unknown") | n/a |
| P2 | `limit` is `non-literal` (variable, env, function) | not_assessed ("limit is not a literal; value cannot be verified"). Never pass | n/a |
| P3 | `kind` is `json`/`urlencoded`/`raw`/`text`, `limit` `default` | bounded (100kb); pass | medium |
| P4 | same kinds, `limit` `literal` and `bytes <= warnBytes` (global) or `<= routeWarnBytes` (route) | pass | medium |
| P5 | same kinds, `limit` `literal` and above the warn threshold for its scope but `<= failBytes` | warning ("limit above recommended maximum for its scope") | medium |
| P6 | same kinds, `limit` `unbounded`, or `literal` with `bytes > failBytes` | fail-candidate (see 3.2 proxy adjustment) | medium |
| P7 | `urlencoded` with `parameterLimit` `unbounded`, or literal above `parameterWarn` | warning (byte cap still applies) | medium |
| P8 | `kind` is `multer`, `limitsObject` is `non-literal` | not_assessed | n/a |
| P9 | `multer`, `limit` (fileSize) `default` or `unbounded` (including `limitsObject: absent`) | fail-candidate ("no file size cap"). Storage `memory`/`disk`/`unknown` is named in evidence | medium |
| P10 | `multer`, fileSize literal above `failBytes` | fail-candidate | medium |
| P11 | `multer`, fileSize literal above the storage threshold (`memory` or `unknown`: `memoryUploadWarnBytes`; `disk`: `diskUploadWarnBytes`) | warning | medium |
| P12 | `multer`, fileSize bounded but `files` or `fields` or `parts` is `default`/`unbounded`, or any is a literal above its warn value, or any is `non-literal` (the last gives not_assessed for that count only) | warning (counts are unbounded or high) | medium |
| P13 | `multer`, fileSize bounded, `files`, `fields` and `parts` all literal and at or below warn values (`fieldSize` default is acceptable) | pass | medium |
| P14 | `kind` is `custom-reader` and `byteCounted` is true | not_assessed ("stream handler with a byte counter; the bound cannot be verified") | n/a |
| P15 | `kind` is `custom-reader`, no byte counter seen | warning ("request stream read directly; no size bound observed"), never fail | low |

`custom-reader` never produces `fail`: streaming to storage is a legitimate design and bounds are often enforced at a proxy or by the store (see traps).

### 3.2 Proxy and server adjustment

Applies to fail-candidates (P6, P9, P10) and to P5/P11 warnings. Evaluate in order.

| # | Condition | Result for the fail-candidate | Confidence |
|---|---|---|---|
| D1 | `proxy.present` is `yes` and `bodyLimitConfig` is `not_supplied` and no `declaredLimit` | warning, never fail ("a proxy is declared and its body-size config was not supplied"). Evidence includes a fixed hint to supply it | low |
| D2 | `proxy.present` is `unknown` (nothing declared) | warning, never fail ("a proxy or gateway not described to this tool may cap request size") | low |
| D3 | `proxy.present` is `yes`, nginx config supplied but `configComplete` is false, or any applicable `clientMaxBodySize` entry is `non-literal` | not_assessed for this declaration | n/a |
| D4 | Supplied proxy cap is bounded (`literal` at or below `failBytes`, including the declared `declaredLimit`) covering the whole app (an `http` or `server` entry, no looser `location` entry with `unlimited` or above `failBytes`) AND `appReachableDirectly` is `no` | warning ("app-level cap missing or high; proxy caps bodies at N bytes; assumes clients cannot reach the app directly") | medium (declared: high) |
| D5 | Same as D4 but `appReachableDirectly` is `yes` or `unknown` | warning, low ("proxy cap can be bypassed or reachability is not declared") | low |
| D6 | Supplied proxy cap is bounded only for some `location` entries and the app has route-agnostic declarations | warning ("proxy cap covers only part of the app"); count of locations only | medium |
| D7 | Supplied proxy config shows `unlimited` (literal 0) or above `failBytes` for the covering scope | fail stays fail (proxy and app both observed unbounded) | medium |
| D8 | `proxy.present` is `no` (declared) | fail stays fail | medium (declared: high) |
| D9 | `proxy.present` is `yes`, nginx config supplied and complete, directive absent in the covering scope | proxy cap is Nginx's default 1 MiB (documented in nginx docs); treat as D4 with `bytes = 1048576`, confidence capped at medium | medium |

The proxy limit is evidence only for the layer it covers. The rule does not model other proxy products beyond a user `declaredLimit`; it never infers a proxy cap from product names.

### 3.3 Aggregation to a single RuleResult

Same single-result contract as BFE-001 (`RuleResult` carries status, confidence, evidence, remediation; severity is the registry default).

| # | Condition | Status | Confidence |
|---|---|---|---|
| A1 | `expressAppFound` is false, or `legacyBodyParser` is true, or `coverage.unresolvedMiddleware` is true with no resolved declarations, or `coverage.complete` is false with no resolved declarations | not_assessed | low (evidence states what was missing) |
| A2 | At least one declaration is a fail after 3.2 | fail | Lowest confidence among failing declarations. Never above medium unless the failing facts come from a declared deployment (high) |
| A3 | No fail, at least one warning | warning | The lowest confidence among warning declarations |
| A4 | No fail/warning, at least one declaration `not_assessed`, or `coverage.complete` is false, or `unresolvedMiddleware` is true | not_assessed | low. Evidence lists the count of unresolved declarations and why |
| A5 | No fail/warning/not_assessed (coverage complete, middleware resolved), at least one declaration `pass` | pass | The lowest confidence among passing declarations |
| A6 | Coverage complete, middleware resolved, Express app found, zero body-reading declarations | pass | low. Evidence: "no body parser, upload handler or stream reader observed; nothing to limit in the analyzed code". Flagged for owner decision 3 |
| A7 | Mixed fail plus not_assessed | fail (A2); evidence lists the unresolved count so the result is not read as complete | per A2 |

Hard constraints:

* No row returns `fail` when `proxy.present` is `yes` with unsupplied body-limit config, or `unknown`. No row returns `fail` for `custom-reader`.
* No row returns `pass` from a `non-literal`, `conditional` or `unresolved` declaration, or from a coverage gap (A4 outranks pass).
* A missing parser is not a failure: a route with no parser reads no body through Express, so there is nothing to limit (Express 4 `req.body` is `{}`, Express 5 `undefined`; neither is evidence).
* `pass` never states or implies "secure", "compliant" or "DoS-proof". Its description is "body-reading declarations were observed with limits within the default thresholds in the supplied evidence".
* `severity` is always the registry default `medium` (the engine has no per-status severity).

## 4. False-positive traps

| Trap | Why it looks insecure | Required behavior |
|---|---|---|
| Limit set at Nginx, an ingress, an API gateway or a CDN (`client_max_body_size`) | App code shows high limits or `multer` without `limits` | D1/D2: warning at low confidence, never fail. If the proxy config is supplied or the user declares the cap, D4 applies |
| Nginx directive absent | Looks like "no limit" | Nginx defaults to `1m` (D9) when the config is supplied and complete; not a missing limit |
| Nginx `location` overrides (`client_max_body_size 0` for `/upload`) | Server-level cap looks sufficient | D6/D7: entries are evaluated per scope; a loose location is not hidden by a tight server cap. Route paths are never echoed |
| Omitted `limit` on `express.json()` | Looks unbounded | P3: default is `100kb` in Express 4 and 5. Pass |
| Per-route parser with a big limit (`app.post("/import", express.json({ limit: "20mb" }), h)`) | Large number | Judged against `routeWarnBytes` (10 MiB), so 20 MiB is a warning at most, and only fail above `failBytes`. A global small parser plus route-scoped larger ones is the recommended pattern |
| Global parser mounted after a route-scoped one, or the reverse | Which limit applies? | Evaluate declarations per scope and kind; do not claim a route is exposed because some other parser is large. Remediation notes mount order |
| Parser mounted only for some paths (`app.use("/api", express.json())`) | Other paths look unprotected | Paths without a parser read no body through Express. Nothing to limit; not a fail |
| Streaming upload piped to object storage with a byte counter or a store-side cap | Reads `req` directly with no parser limit | P14/P15: warning or not_assessed, never fail |
| `limit` as a number of bytes (`limit: 1048576`) or `"1MB"`, `"1 mb"` | Different spelling | Collector normalizes to bytes; matching is case-insensitive |
| `limit` read from `process.env` or config object | Not a literal | P2: not_assessed. Never pass, never fail |
| `multer` with `memoryStorage` and a small `fileSize` | "Uploads in memory" | P13 passes when bounded; storage only moves the warning threshold |
| `multer` `fileSize` bounded, `fieldSize` omitted | Missing key | Default `fieldSize` is 1 MiB (finite); acceptable |
| Example or test code (`*.test.ts`, `examples/`) with unbounded parsers | Not the deployed app | Collector skips test and example directories by default |
| App behind a proxy that rewrites bodies or terminates uploads (e.g. a direct-to-storage presigned flow) | App sees no large bodies | Nothing to flag from code; the rule makes no claim about it (see Limits) |
| `express.raw()` for webhooks with signature checks | Raw buffer parser | Judged like any parser: default 100kb passes. Webhook providers rarely send large bodies |

## 6. Remediation

The engine's `remediation` string contains the neutral block first, then the proxy and Express blocks, with only sections relevant to the findings.

### Framework-neutral

* Choose a body-size cap per content type and enforce it at the earliest layer you control (proxy or gateway), and again in the application so the cap survives deployment changes. Start with a small default (for example 100 KiB for JSON APIs) and raise it only for the specific routes that need more.
* Bound counts as well as bytes: number of urlencoded parameters, multipart fields, files and parts.
* Reject oversized requests with HTTP 413 before reading the body when a `Content-Length` is present, and abort while streaming when it is not (chunked bodies have no declared length).
* For large uploads, prefer streaming to disk or object storage with a per-request byte counter and an upload timeout, rather than buffering in memory.
* If a proxy or gateway already enforces the cap, declare it in the `deployment` block (cap in bytes, and whether clients can reach the app directly), or supply its config, so the next scan can see it.

### Nginx (when the proxy owns the cap)

```nginx
http {
    client_max_body_size 1m;          # default is 1m; set it explicitly

    server {
        location /api/import {
            client_max_body_size 20m; # raise per location, not globally
        }
    }
}
```

`0` disables the check (no limit). Do not use it except behind an upstream cap you have verified.

### Express

```js
import express from "express";
import multer from "multer";

const app = express();

// Small global defaults (these are also the library defaults; explicit is clearer)
app.use(express.json({ limit: "100kb" }));
app.use(express.urlencoded({ extended: false, limit: "100kb", parameterLimit: 1000 }));

// Raise per route, and mount BEFORE any global parser that would parse the same content type first
// app.post("/api/import", express.json({ limit: "5mb" }), importHandler);

// Uploads: multer's limits default to unlimited. Always set them.
const upload = multer({
  storage: multer.diskStorage({ destination: "uploads/" }),
  limits: { fileSize: 5 * 1024 * 1024, files: 4, fields: 20, parts: 30 },
});
app.post("/avatar", upload.single("avatar"), (req, res) => res.sendStatus(204));

// Map parser errors to 413 (body-parser sets err.status and err.type)
app.use((err, req, res, next) => {
  if (res.headersSent) return next(err);
  if (err?.type === "entity.too.large" || err?.code === "LIMIT_FILE_SIZE") {
    return res.status(413).json({ error: "payload too large" });
  }
  return next(err);
});
```

The same code works on Express 4.16+ and 5; byte limits are identical. Do not raise `limit` globally to make one route work. The body-parser documentation advises against values much above the default because payloads of several MB raise memory use and response time. In Express 5, check `req.body` for `undefined` where no parser matched. This guidance is a starting point, not a guarantee of resilience to denial of service.

## 8. Limits

This rule cannot detect, and a pass does not imply anything about:

* What a deployed proxy, CDN, WAF, API gateway or load balancer actually enforces, unless the user declares the cap or supplies the Nginx config. Only Nginx `client_max_body_size` is parsed; other products need a user-declared cap.
* Runtime behavior: limits chosen per request or per tenant, values from `process.env` or config files, middleware order across unresolved modules, parsers added by dependencies or plugins.
* Whether a `limit` is the right size for the application, or whether a bounded body can still be expensive (deeply nested JSON, regex-heavy handlers, decompression ratio with `inflate`, many small requests). Rate limiting (BFE-004) and timeouts are separate controls.
* Slow-body and slow-header attacks, connection limits, `server.requestTimeout`, `headersTimeout` and similar Node settings.
* Streaming handlers: byte counters are noted, not verified. Direct-to-storage upload flows (presigned URLs) never touch the app and are invisible.
* Non-Express servers and frameworks (Fastify `bodyLimit`, Koa, NestJS adapters), serverless platform limits, and multipart libraries other than multer (busboy, formidable) beyond the `custom-reader` heuristic.
* Anything about headers, CORS, cookies or proxy trust (BFE-001, 002, 006, 008).
* A bounded limit says nothing about vulnerabilities elsewhere in the application. Passing means the checked declarations had acceptable limits in the evidence supplied.
