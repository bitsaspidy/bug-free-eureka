## 1. Concern

Express decides who the client is from the `trust proxy` setting. It feeds `req.ip`, `req.ips`, `req.protocol`, `req.secure` and `req.hostname`. If the setting trusts more hops than really exist (`true`, or a hop count above the real proxy chain, or a trusted range that covers untrusted peers), a client can send its own `X-Forwarded-For`, `X-Forwarded-Proto` or `X-Forwarded-Host`, and Express will believe it. In production this means:

* **Rate limiting and lockouts evaded.** A limiter keyed on `req.ip` gets a fresh bucket for every forged address, so brute-force and abuse limits stop working. Allow-lists and IP-based access checks can be bypassed the same way, and audit logs record attacker-chosen addresses.
* **Wrong protocol.** A forged `X-Forwarded-Proto: https` makes `req.secure` true over plain HTTP. `Secure` cookies are sent over HTTP, and HTTPS-redirect middleware is skipped.
* **Host poisoning.** `req.hostname` comes from `X-Forwarded-Host` when proxies are trusted, which can corrupt generated links such as password-reset URLs.

The opposite mistake is also common. Behind a real proxy with `trust proxy` unset, `req.ip` is the proxy's address, so all users share one rate-limit bucket, and behind an HTTPS-terminating proxy `req.secure` is false, so `Secure` cookie logic misbehaves. That case is reported as a warning, because it is a correctness fault and not a spoofing hole. The right value depends on the deployment, so this rule compares the setting with the declared topology and returns `not_assessed` when the topology is unknown. A passing result does not mean the app is secure. It means the setting matched the declared topology in the supplied evidence.

## 2. Inputs & evidence

The rule is a pure function of one typed input built by collectors (AST scanner, config loader). It performs no I/O and never reads the clock, environment or network. It never executes scanned code (CLAUDE.md §1.5), so every value it receives is a literal observed in source or a user declaration.

### 2.1 Proposed input type

```ts
export type Tri = "yes" | "no" | "unknown";

export type TrustProxyValue =
  | { kind: "boolean"; value: boolean }           // true / false; app.enable / app.disable normalised to this
  | { kind: "hops"; hops: number }                // integer literal 0..1000; anything else is "unresolved"
  | { kind: "list"; entries: string[] }           // IPs, CIDRs, ip/netmask, loopback|linklocal|uniquelocal;
                                                  // comma strings are split and trimmed by the collector
  | { kind: "function"; alwaysTrue: boolean };    // alwaysTrue only when the AST body is the literal `true`

export interface TrustedProxyInput {
  app: { expressAppFound: boolean };
  deployment: {                                    // user declaration; the rule never guesses it
    topology: "none" | "single-proxy" | "cdn-plus-lb" | "unknown";   // default "unknown"
    declaredHops?: number;                         // integer 1..16, only with a non-"none"/"unknown" topology
    proxyAddresses: string[];                      // optional declared proxy IPs/CIDRs; may be empty
    directExposure: Tri;                           // can a client reach the app, or any inner hop, without
                                                   // passing every declared proxy? default "unknown"
    forwardedHeaderHandling: "overwrite" | "append" | "unknown";
                                                   // what the OUTERMOST trusted proxy does with a client-supplied
                                                   // X-Forwarded-For. default "unknown"
  };
  trustProxy: {
    state: "not_set" | "set" | "unresolved" | "conditional";
    // set = one literal found; unresolved = env/import/computed value, or several differing assignments,
    // or set on a sub-app that cannot be tied to the serving app; conditional = inside an if / env check
    value?: TrustProxyValue;                       // present only when state is "set"
    location?: string;                             // POSIX "file:line", validated (section 2.3)
  };
  coverage: {
    complete: boolean;                             // false if any limit hit / file skipped / unparsed
    limitsHit: string[];                           // counted only, never echoed
  };
}
```

Input caps (reject, never truncate; the same pattern as `bfe-001-input.ts`): `entries` and `proxyAddresses` at most 64 items of at most 100 characters each; `hops` an integer 0..1000 (the collector emits `unresolved` for anything else, including `NaN`, floats, negatives and numeric strings); `location` at most 500 characters; `limitsHit` at most 200 items of at most 500 characters; schema is a Zod `strictObject`, so unknown keys, `__proto__` and `constructor` keys are rejected. The classifier works on the already-capped strings.

### 2.2 Normalisation (collector side)

| Source form | Normalised |
|---|---|
| `app.set("trust proxy", true)` or `app.enable("trust proxy")` | boolean true |
| `false`, `app.disable("trust proxy")`, or never set | `not_set` / boolean false (same behaviour: socket address) |
| `0` | hops 0 (treated as "off", same as false) |
| `1`, `2`, ... | hops n |
| `"loopback"`, `"loopback, 10.0.0.5"`, `["10.0.0.0/8", ...]` | list |
| Arrow or function expression | function; `alwaysTrue` true only when the body is literally `true` |
| `process.env.X`, a variable, a call, spread, template string | `unresolved` (never guessed) |
| A numeric string such as `"1"` | `unresolved` (Express expects a number or IP strings; the string is not a hop count) |
| Assignment inside `if (...)`, a ternary or an env check | `conditional` |
| Two assignments with different values | `unresolved` |

### 2.3 Evidence ranking, redaction and allowlist

| Source | Meaning | Confidence ceiling |
|---|---|---|
| Declared deployment block (topology, hops, exposure, header handling) | Statement by the user about the real network | high |
| Source AST literal for `trust proxy` | What the code sets | medium (a later call, another module or a sub-app may override) |
| Proxy config supplied and parsed to set `forwardedHeaderHandling` | Whether the proxy overwrites or appends | medium (directive inheritance is partial) |
| `package.json` hints | none used by this rule | n/a |

Redaction and allowlist rules, from the BFE-001 lessons:

* Evidence strings are built only from fixed phrases, the form name (`true`, `hop count`, `address list`, `named list`, `function`, `not set`), the topology name, integers validated as 0..1000, counts of entries, and a `location` that matches `^[\w./-]{1,200}:\d{1,9}$`. A location that does not match is replaced with `unknown-location`.
* IP addresses, CIDRs, entry text, `proxyAddresses`, `limitsHit` text and function source are never echoed, since they describe internal network layout and are user free text. Only counts appear ("3 trusted entries", "2 declared proxy addresses not covered").
* The rule never reads headers, cookies or request samples. No secret can enter the rule input.
* Output is deterministic: classification depends on values only, not on array order (entries are classified as a set).

### 2.4 Classifying a list (pure and deterministic)

Each entry is parsed with a strict grammar (IPv4, IPv6, `addr/prefix`, `addr/netmask`, or exactly `loopback`, `linklocal`, `uniquelocal`, lower-case). Parsing matches proxy-addr behaviour, including IPv4-mapped IPv6 equivalence. A list gets one class, the first that applies:

| Class | Condition | Meaning |
|---|---|---|
| `invalid` | Any entry fails to parse (including capitalised names) | Not assessable. Express can refuse to start with such a value; the rule does not rely on that |
| `trust-all` | Any entry has prefix length 0 (`0.0.0.0/0`, `::/0`), or an IPv6 range containing `::ffff:0:0/96` (for example `::/80`), which also trusts every IPv4-mapped peer | Equivalent to `true` |
| `very-broad` | Any non-private entry with prefix shorter than /16 (IPv4) or /48 (IPv6) | Trusts a wide public range (warning) |
| `private-wide` | Contains `uniquelocal`, or a private CIDR shorter than /16 | Trusts every peer in a private network, such as other tenants, pods or SSRF-reachable neighbours |
| `specific` | Everything else: host IPs, narrow CIDRs, public CDN ranges, `loopback`, `linklocal` | The recommended form |

For `specific` lists, `coversDeclared` is true when every address in `deployment.proxyAddresses` is matched by at least one entry, and `proxyAddresses` is non-empty.

## 3. Decision table

Let `N` be the real proxy hop count from the declaration: `declaredHops` if given, otherwise 0 for `none`, 1 for `single-proxy`, 2 for `cdn-plus-lb`, and undefined for `unknown`. A default-derived `N` caps confidence at medium.

Four forms are collapsed: **off** = `not_set`, `false` or hops 0. **trust-all** = `true`, always-true function, or a list of class `trust-all`. **hops n** with n >= 1. **list** with a class from 2.4.

### 3.1 Gate rows (evaluate first, first match wins)

| # | Condition | Status | Confidence |
|---|---|---|---|
| G1 | `expressAppFound` is false | not_assessed | low |
| G2 | `trustProxy.state` is `unresolved` or `conditional` | not_assessed. Evidence: "value is not a literal" or "set conditionally" and location. Never pass or fail | low |
| G3 | `state` is `not_set` and `coverage.complete` is false | not_assessed ("the setting may be in a file that was not read") | low |
| G4 | `state` is `set` and `coverage.complete` is false | not_assessed (a later assignment may override it; mirrors BFE-001 D7) | low |
| G5 | Value is a `list` of class `invalid`, or a `function` with `alwaysTrue` false | not_assessed ("function body or entry cannot be evaluated"). Function results cannot be known statically | low |

### 3.2 Direct-exposure and trust-all rows (any topology)

| # | Condition | Status | Confidence |
|---|---|---|---|
| E1 | `directExposure` is `yes` AND form is trust-all or hops n | fail ("a client that reaches the app without a proxy can supply forwarded headers that are trusted") | high |
| E2 | Topology `none` AND form is trust-all or hops n | fail | high |
| E3 | Form is trust-all AND `forwardedHeaderHandling` is `append` (declared) | fail ("the outermost trusted proxy appends to a client-supplied header, so the left-most entry is client-controlled") | high |

### 3.3 Per-topology rows (when no gate or E row matched)

| # | Topology | Form | Condition | Status | Severity | Confidence |
|---|---|---|---|---|---|---|
| T1 | none | off | | pass | high | high (declared) |
| T2 | none | list (specific, private-wide, very-broad) | | warning ("trusted addresses configured although no proxy is declared") | high | medium |
| T3 | single-proxy or cdn-plus-lb | off | | warning (`req.ip` is a proxy address; clients share one bucket; `req.secure` is wrong when TLS ends at the proxy; not a spoofing fault) | high | medium |

| T17 | unknown | list (any valid class) | | not_assessed | high | low |

### 3.4 Hard constraints

* No `fail` from absence, an unknown value, or code alone. A `fail` always cites a declared fact (topology `none`, `directExposure: yes`, `forwardedHeaderHandling: append`, or a declared hop count lower than the configured one).
* Behind a proxy with unknown configuration (`directExposure` or `forwardedHeaderHandling` unknown), the result is `not_assessed` or `warning`, never `fail` (T5, T8, T14 to T17).
* `pass` only when the setting is a literal, coverage is complete, the topology is declared, and a declaration supports it (T1, T7, T10). `unresolved`, `conditional`, functions and unknown topology never pass.
* `pass` never states or implies "secure" or "compliant". Its description is "the trust proxy setting matches the declared topology in the supplied evidence".
* `severity` is always the rule default `high`; the engine contract (`RuleResult`) carries no per-status severity. See owner decisions in the hand-off.
* Evidence also states, as fixed text, which Express properties depend on the setting (`req.ip`, `req.ips`, `req.protocol`, `req.secure`, `req.hostname`).

## 4. False-positive traps

| Trap | Why it looks insecure | Required behavior |
|---|---|---|
| `trust proxy: true` behind a proxy that always overwrites `X-Forwarded-For` and cannot be bypassed | `true` trusts all hops | T4 `warning` at most, never fail. With `forwardedHeaderHandling` unknown, T5 `warning`, low |
| `trust proxy: 1` | Looks arbitrary | Pass when topology is one proxy and exposure is declared `no` (T7). With an unknown topology, `not_assessed`, not warning |
| A trusted list containing a public CIDR | Public ranges look suspicious | A CDN's published ranges are the intended use. Class `specific`; only prefix shorter than /16 (IPv4) or /48 (IPv6) is `very-broad` |
| `loopback` | Looks like trusting everything local | Correct for a same-host Nginx or sidecar. `specific`. Pass requires a declared matching `proxyAddresses` entry; otherwise T11 `not_assessed` |
| `uniquelocal` in a Kubernetes or VPC deployment | Looks broad | Common and often necessary, but still `private-wide` (T13 warning, medium). The text says the narrower subnet is preferable. Never fail |
| `trust proxy` unset, app declared as `none` | Looks like a missing setting | T1 pass. Unset is the safe default with no proxy |
| `trust proxy` unset with an unknown topology | Might be a missing setting | T14 `not_assessed`, not warning |
| Value from `process.env.TRUST_PROXY` or a config file | Not a literal | G2 `not_assessed`. The remediation explains how to validate it. Never guessed, never pass |
| Setting inside `if (process.env.NODE_ENV === "production")` | Not visibly active | `conditional`, G2 `not_assessed` |
| A function such as `(ip) => ip === "10.0.0.5"` | May be correct or not | G5 `not_assessed`. Only the literal body `true` is classified (trust-all) |
| Proxy overwrites `X-Forwarded-For` with `$remote_addr` (Nginx), but the user did not declare it | Handling unknown | `unknown`, never assume overwrite or append (CLAUDE.md §1.4) |
| `directExposure: unknown` with a correct hop count | No proof clients cannot bypass the proxy | T8 `warning`, low. Not fail, and not pass |
| Hop count lower than the real chain | Looks like under-trust | T9 warning only (wrong `req.ip`, not spoofable) |
| `app.enable("trust proxy")` / `app.disable("trust proxy")` | Not `app.set` | Normalised to boolean (2.2) |
| Sub-app with its own `trust proxy`, mounted on the main app | Ambiguous app | `unresolved`, G2 `not_assessed` unless tied to the serving app |
| Test code, `examples/` | Not the deployed app | Collector skips them by default |
| App code that never reads `req.ip` or `req.protocol` | The setting still looks unsafe | Still reported; libraries and middleware may read them. Evidence does not claim exploitability |

## 6. Remediation

The engine's `remediation` string should contain the neutral block first, then the Express block, with only sections relevant to the form found.

### Framework-neutral

1. Draw the real path from the internet to the app and count the proxy hops you control (CDN, load balancer, ingress, sidecar). Trust exactly that many hops, or exactly those addresses. Do not use "trust everything".
2. Make the outermost trusted proxy set the client address itself instead of forwarding what the client sent. In Nginx, `proxy_set_header X-Forwarded-For $remote_addr;` overwrites. `$proxy_add_x_forwarded_for` appends to a client-supplied value, which is safe only if the app trusts the right number of hops. Also set `X-Forwarded-Proto` and `X-Forwarded-Host` explicitly rather than passing through client values. Cloud load balancers and CDNs document their own behaviour, so check it.
3. Make the app reachable only through the proxy: restrict the origin's firewall or security group to the proxy or CDN address ranges, or use mutual TLS or an authenticated origin pull. A hop count is only correct if no path is shorter than the declared chain.
4. Prefer an address list of your proxies' subnets over a hop count when the chain can change (autoscaling, multi-tier CDNs). With a list, a client that reaches the app directly is simply not trusted.
5. Declare the topology in the `deployment` block (`topology`, `declaredHops`, `proxyAddresses`, `directExposure`, `forwardedHeaderHandling`) so the next scan can confirm the setting instead of returning `not_assessed`.
6. If a limiter or allow-list keys on the client address, check it after the change. Send a request with a forged `X-Forwarded-For` through the real entry point and confirm that the address the app logs is not the forged one.

### Express

```js
import express from "express";
const app = express();

// No proxy in front (local, direct deployment): leave the default, or be explicit.
app.set("trust proxy", false);

// One proxy (for example Nginx or one load balancer) directly in front of the app:
app.set("trust proxy", 1);

// CDN + load balancer, both under your control: trust exactly two hops...
app.set("trust proxy", 2);

// ...or, better, trust only your proxies' addresses. A direct client is then never trusted.
app.set("trust proxy", ["loopback", "10.0.1.0/28", "173.245.48.0/20"]);
```

Reading the value from the environment (note that Express does not accept the string `"1"` as a hop count, so convert it):

```js
const raw = process.env.TRUST_PROXY_HOPS ?? "0";
const hops = Number.parseInt(raw, 10);
if (!Number.isInteger(hops) || hops < 0 || hops > 5) {
  throw new Error("TRUST_PROXY_HOPS must be an integer from 0 to 5");
}
app.set("trust proxy", hops);
```

Set it before middleware that reads `req.ip`, such as rate limiters, session middleware and audit logging. For session cookies behind a TLS-terminating proxy, a correct `trust proxy` makes `req.secure` true so that `Secure` cookies work. Never use `app.set("trust proxy", true)` on an app that clients can reach directly. The same settings work on Express 4 and 5. A Supertest check (test code only; do not add a debug route to production):

```js
import request from "supertest";

it("ignores a forged X-Forwarded-For from a client that is not a trusted proxy", async () => {
  const res = await request(app).get("/whoami").set("X-Forwarded-For", "203.0.113.9");
  expect(res.body.ip).not.toBe("203.0.113.9"); // /whoami returns { ip: req.ip } in the test app only
});
```

## 8. Limits

This rule cannot detect, and a pass does not imply anything about:

* Whether the declared topology is true. All topology facts are user declarations. A stale or wrong declaration gives a wrong result.
* Actual proxy behaviour. It does not read or parse Nginx, HAProxy, cloud load balancer or CDN config in v0.1 (only the user's declared `forwardedHeaderHandling`), so it cannot see whether a proxy overwrites, appends or passes through client headers.
* Whether the origin is reachable around the proxy (public IP, a second listener, internal network access). It only uses the declared `directExposure`.
* Runtime or per-request values: settings changed after startup, set in code the collector did not reach, differing per environment, or computed from the environment. Those are `unresolved`/`conditional` and give `not_assessed`.
* What a custom function does beyond a literal `true`.
* Code that reads `req.headers["x-forwarded-for"]`, `x-real-ip`, `forwarded` or `cf-connecting-ip` directly and bypasses `trust proxy`. A later rule or collector may flag direct reads.
* The consumers of `req.ip`: whether a rate limiter, allow-list or audit log is present, keyed on the right value, or backed by a shared store (BFE-004).
* Cookie flags, HSTS or CORS configuration (BFE-001, 002, 008), and IPv6 grouping choices in limiters.
* Non-Express servers (Fastify's `trustProxy`, Koa's `app.proxy`): reported as `not_assessed`.
* Whether the application is vulnerable beyond this setting. Correct trust settings reduce one class of spoofing; they do not remove other defects.
