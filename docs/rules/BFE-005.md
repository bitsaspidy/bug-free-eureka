# BFE-005: Sensitive data in configured logging

| Field | Value |
|---|---|

| Rule version | `1.0.0` |

## 1. Concern

Request loggers often write whole headers or bodies. Then `Authorization` and `Cookie` headers, `Set-Cookie` responses, passwords, OTPs and access or refresh tokens end up in log files, log shippers and dashboards, where many more people and systems can read them than can read the database. A leaked session cookie or refresh token is a working credential (CWE-532).

This rule reads the declared logging configuration (Pino, pino-http, winston, express-winston, morgan, bunyan, `console` call sites) and reports which sensitive parts are written without redaction. A pass means no unredacted sensitive data was found in the supplied configuration. It is not a guarantee about what the application logs at run time.

## 2. Inputs & evidence

The rule is a pure function of one typed input built by collectors (AST scanner, config loader). It performs no I/O and never executes scanned code.

### 2.1 Input type (`SensitiveLoggingInput`)

```ts
type Tri = "yes" | "no" | "unknown";
interface SensitiveLoggingInput {
  app: { expressAppFound: boolean };
  loggers: Array<{                       // max 100
    library: "pino" | "pino-http" | "winston" | "express-winston" | "morgan" | "bunyan" | "console" | "other";
    kind: "request" | "call";            // per-request middleware or one log call site
    scope: "global" | "route" | "conditional" | "unresolved";
    location: string;                    // "file:line", max 500 chars
    emits: { requestHeaders: Tri; responseHeaders: Tri; requestBody: Tri; query: Tri };
    redaction:
      | { state: "none" }
      | { state: "paths"; paths: string[] } // literal Pino-style paths, max 200 x 200 chars
      | { state: "unresolved" };            // variable, function or custom format
  }>;
  coverage: { complete: boolean; limitsHit: string[] };
}
```

Paths are relative to the log object root, as Pino uses them (`req.headers.authorization`, `res.headers["set-cookie"]`, `req.body`). Oversized or malformed input is rejected, never truncated.

### 2.2 Sensitive categories

| Part | Categories (exact keys) |
|---|---|
| request headers | `authorization`, `proxy-authorization`, `cookie`, `x-api-key` |
| response headers | `set-cookie` |
| request body | password (`password`, `passwd`, `pwd`), OTP (`otp`, `totp`, `code`, `mfaCode`, `mfa_code`), refresh token, access token (`accessToken`, `access_token`, `token`, `idToken`, `id_token`) |
| query | whole query string or URL |

A path covers a key when it ends in `<container>.<key>` with an exact, case-sensitive key (Pino is case-sensitive; Node lower-cases header names). `req.*.cookie` counts; a root wildcard such as `*.cookie` does not, because a Pino wildcard matches one level only. A path naming the other side (`res…` for a request part) never counts. Removing the whole container (`req.headers`, `req.headers.*`, `req.body`, `req.query`, `req.url`) covers every key in it. Unparseable paths cover nothing.

### 2.3 Evidence

One evidence item per logger (max 20, then a count): library, kind, scope, the parts it writes, the redaction state and number of paths, the names of unredacted categories, and the reason. Locations are echoed only when they are a safe relative `file.ext:line`; otherwise `unknown-location`. Redact paths, location text and limit text are never echoed. The engine also passes all evidence through `maskSecrets`.

## 3. Decision table

Per logger:

| Condition | Result |
|---|---|
| writes no part (all `no`) | pass, high |
| redaction `unresolved` | not_assessed, low |
| request/response headers `yes` with an unredacted category | fail |
| request body `yes`, a body category not covered and body not removed | fail |
| request body `yes`, every category covered only by field paths | warning, medium (nested or differently cased fields are not covered) |
| query `yes`, query/URL not removed | warning, medium |
| any part `unknown` and not fully removed | not_assessed, low |
| everything written is removed | pass, high |

A fail has high confidence when the location is a safe `file:line` and scope is `global` or `route`, otherwise medium.

Overall: no Express app → not_assessed (low). No loggers → pass (medium) if coverage is complete, else not_assessed (low). Otherwise the worst logger result wins, in the order fail > warning > not_assessed > pass, with the highest confidence among loggers at that status. A pass with incomplete coverage becomes not_assessed (low). Invalid input → not_assessed (low) with `input invalid: <paths>` and no values.

## 5. Redaction utility

`redact(value, options)` returns a JSON-safe copy where values under sensitive keys become `****` and every other string goes through `maskSecrets`. Keys are compared after lower-casing and removing `-`, `_`, `.` and spaces; exact keys (`otp`, `pin`, `sid`, `session`, `jwt`, `pwd`, …) and key parts (`password`, `secret`, `token`, `apikey`, `authorization`, `cookie`, `credential`, `privatekey`, …). `extraKeys` adds more. It handles nested objects, arrays, `Map`, `Set`, `Date`, `Error` (name, message, stack, own fields) and hostile input: cycles become `[Circular]`, depth over `maxDepth` (8) `[MaxDepth]`, more than `maxNodes` (2000) values `[Truncated]`, getters are never called (`[Getter]`), and a throwing Proxy gives `[Unredactable]`. Key names are masked as text too. `redactHeaders` lower-cases header names first. Over-redaction (for example a field named `tokenizer`) is accepted on purpose.

## 6. Remediation

Log only what you need (method, route, status, duration, request id). With Pino set `redact.paths` for the headers above and remove `req.body` entirely; with express-winston use `requestWhitelist` and `headerBlacklist`; with morgan use a format without query strings. Then run a canary test against your real logger output.

## 7. Known limitations

* Field-level body redaction is never a pass, because the rule cannot know body shapes.
* Custom serializers and winston formats are `unresolved` unless the collector can prove their output.
* Query strings are a warning, not a fail: whether they carry secrets depends on the app.
